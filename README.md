# synth-verify

> Synthetic training-data pipeline with **separate-model verification** and structural heuristics. On a real 200-example NLI synthesis run with Llama-3.1-8B as generator and Llama-3.3-70B as verifier, the verifier rejects **32% of examples** as mislabeled or weakly grounded — the kind of errors that would poison a fine-tune.

## Hero benchmark

200 NLI training examples generated by `llama-3.1-8b-instant`, then run through structural heuristics and a `llama-3.3-70b-versatile` verifier — both via Groq's free tier, so the whole benchmark costs $0.

| Stage | Pass rate | Notes |
|---|---:|---|
| **Generation** | 200 / 200 | 0 parse failures, batches of 5 with rotating topical seeds |
| **Heuristic gate** | 199 / 200 (99.5%) | 1 near-duplicate caught by hash signature comparison |
| **Verifier (Llama-3.3-70B)** | 135 / 199 (67.8%) | 64 examples rejected for label / entailment errors |
| **Overall verified** | **135 / 200 (67.5%)** | survives both gates → ready for fine-tuning |

### What the verifier actually caught

| Rejected example (Llama-3.1-8B labeled it `entailment`) | Verifier's reason |
|---|---|
| premise: "The Treaty of Versailles was signed on June 28, 1919." hypothesis: "The Treaty of Versailles imposed harsh penalties on Germany." | The hypothesis is not entailed by the premise, which only states the signing date. |
| premise: "The Rosetta Stone was discovered in 1799." hypothesis: "The Rosetta Stone helped decipher ancient Egyptian hieroglyphics." | Hypothesis requires external knowledge. |
| premise: "The FIFA World Cup is held every four years." hypothesis: "It is a popular international event." | Hypothesis adds an opinion that the premise doesn't support. |
| premise: "Spring is a season of renewal..." hypothesis: "Some plants continue to bloom during winter..." (labeled `contradiction`) | Hypothesis describes a different aspect; not a contradiction. |

These are exactly the failure modes a fine-tune doesn't catch on its own — the model generates a plausible-looking triple, labels it confidently, and a downstream classifier learns the wrong patterns.

## Why this exists

A common LLM-team failure pattern: "let's just have the model generate training data." The generator is overconfident, ships labels that look right, and you don't notice the rot until a downstream metric tanks.

`synth-verify` ships the three pieces every team eventually builds themselves, glued together:

1. **Generator** — prompts an LLM to produce examples for a `TaskSpec`, rotating through diversity seeds so the batches don't all sit on the same topic.
2. **Heuristic gate** — cheap structural checks (format, label-validity, leakage, near-duplicate) that run **before** the verifier so you don't pay verifier-LLM tokens on malformed examples.
3. **Verifier** — a **different** LLM scores each surviving example against the task spec. The pipeline enforces "different LLM" at construction time so you can't accidentally have the generator grade its own work.

Output is a JSONL where every example carries its full audit trail — heuristic results, verifier verdict, verifier reason. You can filter on `score.passed` to ship, or inspect rejections to retune the prompt.

## Quickstart

```bash
pip install -e ".[groq]"
export GROQ_API_KEY=gsk_...
```

```python
from synth_verify import (
    GroqClient, Pipeline, Generator, Verifier, HeuristicChecks, TaskSpec,
)

spec = TaskSpec(
    name="nli",
    description=(
        "Generate Natural Language Inference triples. The label must accurately "
        "describe whether the hypothesis follows from the premise."
    ),
    label_field="label",
    valid_labels=["entailment", "contradiction", "neutral"],
    text_fields=["premise", "hypothesis"],
    schema_hint={
        "premise": "a 5-25 word factual sentence",
        "hypothesis": "a 5-15 word claim",
        "label": "string in {entailment, contradiction, neutral}",
    },
    diversity_seeds=["cooking", "sports", "history", "music", "wildlife"],
)

pipeline = Pipeline(
    spec,
    generator=Generator(GroqClient(model="llama-3.1-8b-instant"), spec, batch_size=5),
    verifier=Verifier(GroqClient(model="llama-3.3-70b-versatile"), spec),
)

result = pipeline.run(n_examples=200)
print(f"Overall pass rate: {result.pass_rate:.1%}")
print(f"Failures: {result.failure_breakdown()}")

verified = [ex.data for ex in result.examples if ex.score.passed]
# verified is your training set
```

The `Pipeline` raises if the generator and verifier share an LLM instance. This is intentional — having the same model grade itself defeats the entire mechanism.

## Built-in heuristic checks

| Check | Catches |
|---|---|
| `format_valid` | missing required field, wrong type |
| `label_valid` | label not in `TaskSpec.valid_labels` |
| `no_leakage` | premise ≈ hypothesis (longest-common-substring ratio over threshold) |
| `length_ok` | text fields shorter than `min_text_len` |
| `no_near_duplicate` | example near-duplicates one already seen this run |

Disable individual checks via `HeuristicChecks(spec, enabled={"no_leakage": False})`. Add your own by extending the class or subclassing.

## Adapters

| Client | Notes |
|---|---|
| `GroqClient` | Default for free runs. Rate-limited (default 2.1s/call ⇒ ~28 RPM) to stay under the 30 RPM free-tier ceiling. |
| `AnthropicClient` | When you need Claude Haiku 4.5 / Sonnet 4.6 quality. |
| `MockLLMClient` | Tests. Deterministic, no network, no cost. |

You can also pass any object implementing the `LLMClient` protocol (a single `complete(prompt, system=..., max_tokens=...) -> CompletionResult`).

## Limitations

**The hero pass rate depends on generator quality.** With Llama-3.1-8B as the generator the verifier rejects 32% of examples. With a stronger generator (Claude Haiku, GPT-4o-mini) the rejection rate would drop — and conversely, with an even cheaper generator (3B-parameter local model) it would rise. The 67.5% number is honest for the cheapest-free-generator scenario, not the ceiling.

**The verifier can be wrong too.** A separate LLM is a better second-opinion than the same model grading itself, but it's not ground truth. For tasks with subtle correct-label boundaries, gold-standard human review on a sample is the only ground truth — `synth-verify` shrinks the human-review burden by filtering obvious failures first.

**No downstream-classifier comparison wired in.** Project IDEAS.md set "verified examples outperform raw on a downstream classifier by ≥ 4 points" as a stretch goal. That's a separate experiment (train two classifiers, compare on a held-out test set) and out of scope for the v0.1 pipeline. The verifier rejection examples in the README make the case qualitatively.

**Diversity seeds are a heuristic, not a guarantee.** The generator rotates through `TaskSpec.diversity_seeds`, but two batches under different seeds can still produce semantically overlapping examples. The `no_near_duplicate` check is a second line of defense; on this 200-example run it caught 1 duplicate.
